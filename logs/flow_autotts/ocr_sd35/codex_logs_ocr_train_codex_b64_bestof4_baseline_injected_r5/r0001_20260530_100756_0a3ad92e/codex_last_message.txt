Implemented [`flow_autotts/controllers/optimal.py`](/inspire/hdd/global_user/gongjingjing-25039/sywang/jkcai/FlowEvo_ocr/flow_autotts/controllers/optimal.py) as a beta-scheduled preview-feedback controller. The idea is a staged policy: start with one scout root, optionally open a second scout root when the first preview is weak or uncertain, finish only the best-ranked survivors, then spend extra beta budget on gap-aware confirmation and anchor-local backward refinement. The new mechanism relative to the recent best controller is that late compute is no longer spent by a mostly fixed refinement loop; it now adapts to preview score gap and uncertainty, and it has an explicit tail-budget repair pass that can open an extra finished scout root or do one more local refinement to avoid avoidable underuse at mid/high beta.

From the frontier rows in the context pack, the latest rewards / mean NFE were: `beta=0.0 -> 0.3581 / 7`, `0.25 -> 0.5920 / 22`, `0.5 -> 0.7018 / 35`, `0.75 -> 0.7765 / 47`, `1.0 -> 0.8071 / 61`. Versus the matched ODE baseline, `0.0`, `0.25`, and `0.75` were above; `0.5` and `1.0` were below. There was only one prior proposal snapshot, so there were not “last two” snapshots to compare; the immediate weakness to target was the under-target, slightly under-computed `beta=0.5` and `beta=1.0` regimes.

The beta schedule is explicit and monotone in target willingness to spend compute: `target_nfe = {0.0:10, 0.25:20, 0.5:36, 0.75:48, 1.0:64}` clipped by `env.budget`; `allow_second_root` turns on from `beta>=0.25`; `survivor_count` increases from `1` to `2` at higher beta; `confirm_rounds` rises from `1` to `3`; `backward_children` rises from `0` to `3`; `backward_time` moves earlier with beta; pruning becomes less aggressive with beta; and `tail_rounds` rise with beta. That keeps larger beta strictly more willing to use width, depth, confirmation, refinement, and later stopping. For each beta: `0.0` targets `10` and stays near a single-root deterministic regime with one extra confirmation only if affordable; underuse is mostly justified because this regime already beat baseline strongly, but I still nudged it toward `10` with a tail confirmation option. `0.25` targets `20`; it can open a second scout root only if the first preview is weak/uncertain, so any mild underuse is intended rather than conservative by accident. `0.5` targets `36`; I adjusted this regime specifically with a second-root option plus tail-root repair so unused budget is more likely to become one more fully previewed candidate or confirmation rather than go unspent. `0.75` targets `48`; it was already above baseline, so underuse was likely justified, but the new tail pass should still keep it close through extra confirmation or one more local child. `1.0` targets `64`; I adjusted this regime most directly with the same tail repair and more confirmation/refinement. It avoids exceeding `64` because every spend path is guarded by `_can_afford(...)`, which checks both `target_nfe` and `env.budget_left`, and here `target_nfe` itself is clamped to `64`.

Actions in the prior best were concentrated in previews plus one-root backward refinement, with very little width on average. This proposal shifts some high-beta budget into evidence-conditioned width and late confirmation instead of only cycling backward from the current best anchor. The intended improvement is mainly `beta=0.5` and `beta=1.0`, with some possibility of preserving or slightly strengthening `beta=0.75`; the main risk is that extra tail roots at mid/high beta may dilute compute if OCR score gaps are already reliable enough after the first completion. I ran `python -m py_compile flow_autotts/controllers/optimal.py` and a tiny fake-env dry run over all betas; the dry run stayed within monotone budget shape and below the `beta=1` hard cap, with approximate NFE usage `8, 19, 35, 47, 62`.
