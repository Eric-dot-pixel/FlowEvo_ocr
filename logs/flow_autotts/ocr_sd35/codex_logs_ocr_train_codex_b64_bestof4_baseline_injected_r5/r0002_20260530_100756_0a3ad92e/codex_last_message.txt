**Controller Idea**
The policy is a single-root, preview-first controller with a new probe-before-commit refinement loop. It builds a root preview ladder, then uses `backward` children as cheap local probes: each child gets an immediate preview at the backward target time, and only children that are competitive on score or reduce uncertainty/drift earn the expensive promotion to `t=0.9/1.0` plus a late confirmation preview. Tail budget is then spent on ambiguity-driven confirmation or one more local probe, rather than blindly finishing more branches.

**Beta Schedule**
The schedule is explicit in `_schedule(beta)` and monotonic in willingness to spend:
- `beta=0.0`: target `10`; root probes `(0.6, 0.8)`; no backward children.
- `beta=0.25`: target `20`; root probes `(0.5, 0.8, 0.9)`; `2` child probes, `1` child commit.
- `beta=0.5`: target `36`; root probes `(0.5, 0.7, 0.9)`; `4` child probes, `2` child commits.
- `beta=0.75`: target `48`; root probes `(0.4, 0.6, 0.8, 0.9)`; `6` child probes, `3` child commits, `mixed_noise`.
- `beta=1.0`: target `64`; same root ladder, but `8` child probes, `4` child commits, wider anchor pool, more tail rounds.

Monotonicity comes from increasing or loosening:
- probe count,
- child probe budget,
- child commit budget,
- anchor pool,
- tail rounds,
- later promotion time,
- gentler exploration noise at high beta.

`beta=1.0` cannot exceed `64` because every costly `forward`/`preview` path is guarded by `_can_afford(..., target_nfe=64, ...)`, `target_nfe=min(env.budget, 64)`, and final termination uses `answer(rule="best_preview_score")`, which has no implicit completion cost.

**What’s New**
Behaviorally new relative to the incumbent:
- backward children are previewed immediately at the backward target time before earning finish budget;
- promotion is adaptive from score gap and uncertainty/drift improvement, not just “spawn child then finish it”;
- anchors are reused more evenly via `anchor_uses`, which preserves diversity at high beta without opening many roots;
- tail spend is ambiguity-driven confirmation or one more selective local probe, aimed specifically at the weak `beta=0.5` and `beta=1.0` regimes.

**Target-NFE Reflection**
Injected references:
- `beta=0.0 -> 10`
- `beta=0.25 -> 20`
- `beta=0.5 -> 36`
- `beta=0.75 -> 48`
- `beta=1.0 -> 64`

Per beta:
- `0.0`: underuse in old controller looked unnecessary relative to the locked `10`. I adjusted it upward with a two-preview root ladder and no branching; intended to stay near `10` without wasting compute on refinement.
- `0.25`: old controller was already above baseline and near target. I kept compute modest; any residual underuse is more likely justified than harmful. The child-probe budget is capped tightly to avoid low-beta waste.
- `0.5`: this is the main repair target. Old run trailed baseline at `35 vs 36` NFE. I increased evidence-gathering and selective refinement so this regime can use more of the target budget through child probes, promotion, and tail confirmation.
- `0.75`: old run already beat baseline near target. I changed allocation, not just volume: more selective child screening and gentler high-beta pruning should preserve the strong result while keeping spend comparable.
- `1.0`: old run trailed baseline and underused at `61 vs 64`. I explicitly added more child probes, more commits, larger anchor pool, and longer tail confirmation to improve utilization when evidence remains ambiguous, while all costly actions remain capped below the hard `64`.

Main risk: because this controller stays single-root, if SD3.5 OCR needs fresh global diversity rather than local refinement at high beta, `beta=1.0` could still underuse or miss some wins. The proposal is meant primarily to improve `beta=0.5` and `beta=1.0` without regressing the already-strong `0.25` and `0.75` rows.
